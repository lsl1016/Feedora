# Feedora 文档规范

本文件是本项目文档的**唯一权威规范**。所有人和 Agent 写文档前应先读本文；
其他地方（README、AGENTS.md、CLAUDE.md）只应指向本文，不要复述规则，避免多处不一致。

## 1. 文档分类

| 类型 | 目录 | 职责 | 生命周期 |
|------|------|------|----------|
| 系统功能文档 | `docs/system/` | 描述模块当前完整功能、接口、核心逻辑 | 长期维护，持续更新 |
| 变更记录文档 | `docs/changelog/` | 记录用户要求留档的代码变更的背景、改动点、影响范围 | 积累后合并到系统文档；merged/archived 可删 |
| 历史设计文档 | `Feedora-backend/docs/`、`Feedora-frontend/docs/` | 各阶段设计快照与专项规范，生成时点的记录 | 只读保留，不追随代码更新 |

系统文档回答"**现在是什么样**"，变更文档回答"**为什么变成这样**"。
历史设计文档（阶段一/阶段二 MVP 设计、原型文档、observability 设计等）是设计时点的快照，与代码演进脱节属正常现象，不回头修改。

## 2. 元信息规范

每篇文档顶部**必须**包含 YAML front-matter，9 个字段全部必填，不得自创字段：

```yaml
---
title: <文档标题>
date: YYYY-MM-DD
version: vX.Y
type: system | changelog
module: <单一业务模块名>
maintainer: <维护人>
status: active | merged | archived
related_code:
  - path/to/file1.go
  - path/to/file2.go
summary: <一句话摘要>
---
```

| 字段 | 说明 |
|------|------|
| title | 文档标题 |
| date | 创建或最近更新日期，格式 `YYYY-MM-DD` |
| version | **文档自身**的版本号，格式 `vX.Y`。不是发布版本号，也不要跟随其他文档的版本 |
| type | `system`（系统文档）或 `changelog`（变更记录） |
| module | 所属业务模块。必须是**单一**模块名，不能是代码包路径（`service/chart` ✗），不能是逗号列表（`chart, dataset` ✗） |
| maintainer | 当前维护人 |
| status | `active`（有效）/ `merged`（已合并到系统文档）/ `archived`（已归档）。不要自创 `pending`、`draft`、`dev` 等值 |
| related_code | 关联代码文件路径列表，**至少 1 个**。这是代码到文档的唯一链接机制 |
| summary | 一句话概括文档内容 |

模块枚举值（本项目实际模块）：
`auth` | `user` | `post` | `comment` | `circle` | `topic` | `tag` | `follow` | `interaction` | `notification` | `file` | `search` | `rank` | `growth` | `admin` | `infrastructure`

## 3. 命名规范

### 3.1 系统功能文档

- 路径：`docs/system/<模块名>.md`，模块名用英文小写
- 每个模块**只保留一篇**主文档

### 3.2 变更记录文档

- 路径：`docs/changelog/YYYYMMDD_vX.Y_<主题说明>.md`
- 示例：`docs/changelog/20260909_v1.0_关注系统上线.md`
- 日期为变更实施日期，版本号为**文档自身**版本
- 同一主题被反复修订时递增次版本号：`v1.0` → `v1.1` → `v1.2`
- 主题用中文，下划线分隔，修复类以「修复」开头、新增类以「新增」开头
- **不使用**日期区间（`20260616-20260902_...` ✗），一篇文档对应一个时间点

## 4. 系统文档结构模板

```markdown
# <模块名>模块功能文档

## 1. 模块概述
## 2. 接口清单
| 路径 | 方法 | 功能 | 控制器 |
## 3. 核心逻辑
### 3.1 <功能点1>
## 4. 数据模型
## 5. 配置项
## 6. 历史版本
| 版本 | 日期 | 修改人 | 变更说明 |
```

§1-§3 固定必有，§4-§5 可按模块特点增减或改名（如"配置项与限制"），
中间可插入模块特有章节（如"测试"）。**"历史版本"始终是最后一节**，版本倒序。

本项目的接口前缀统一为 `/api/v1`，接口清单中的路径可省略该前缀。
控制器列填 `internal/api` 中的处理函数名。

## 5. 变更文档结构模板

```markdown
# <变更主题>

## 1. 背景与目标
## 2. 代码改动
- 文件：`path/to/file.go`
  - 改动说明：
## 3. 影响范围
- 接口：
- 模块：
- 配置：
## 4. 测试验证
- 命令：
- 结果：
## 5. 风险与兼容性
## 6. 历史版本
| 版本 | 日期 | 修改人 | 变更说明 |
```

章节用 `## 1.` 阿拉伯数字编号，不用「一、二、三」。章节名不要改写。

修复类变更在 §1 内展开三个子节：`### 问题描述` / `### 根因分析` / `### 影响范围`。

§4 必须写**真实执行过的命令和结论**，不写"已测试"这类无凭据的话。

## 6. 定期整合机制

### 6.1 触发条件

当某模块在 `docs/changelog/` 中 **status 为 active** 的文档累计超过 **5 篇**时，触发一次整合。

### 6.2 整合流程

五步全部执行，不可跳过第 4、5 步：

1. 阅读该模块所有 active 状态的 changelog
2. 将核心内容合并到 `docs/system/<模块>.md`（事实性内容进对应章节，不是追加一节"历史变更"）
3. 递增系统文档的 `version`，更新 `date`
4. 将已合并的 changelog 的 `status` 由 `active` 改为 `merged` —— **逐个文件都要改**
5. 在系统文档"历史版本"表新增一行，记录本次整合

### 6.3 原则

- `status: active` 的 changelog **不删除**，仅整合后改 `status`；`merged` / `archived` 状态的文件**允许删除**（事实已进系统文档或已废弃），是否清理由用户决定
- 同主题只保留一篇系统文档，禁止产生 `xxx_v2`、`xxx_最终版` 等并行文档
- 若必须拆分子文档，需在系统文档中增加索引并说明职责边界

## 7. 与代码变更的联动

**变更记录按需生成，不自动触发。** 只有用户给出明确信号时才在 `docs/changelog/` 下新增变更记录文档，信号词如：「写变更记录」「生成 changelog」「记录这次改动」「补变更文档」、`/changelog`。

默认（无信号）：代码变更完成后直接收尾，**不生成 changelog，也不追问要不要生成** —— 每次改动都自动生成会显著拖慢任务。

## 8. 数据与接口规范

### 8.1 计数维护

- 每个计数列（`post_count`、`comment_count`、`use_count` 等）有**唯一 owner**：变更只能发生在拥有该聚合的事务边界内（如帖子计数只出现在 `post_repository` 的事务方法里），Service 层不得额外增减
- 创建与删除必须**对称**：创建时 +1 的所有计数，删除时在同一个事务里以 `GREATEST(col - 1, 0)` 回减
- 计数只统计**已发布/生效**状态；草稿、定时等中间状态不占计数，转正时补齐

### 8.2 软删除语义

- `status` 列是业务状态机的**唯一事实来源**（normal/deleted、published/hidden/takedown 等），业务判断一律看 `status`
- `deleted_at` 仅服务于 GORM 查询的默认过滤；不允许出现"status 已置 deleted 但 deleted_at 为空"之外的双标志混用（唯一例外：评论占位节点——有子回复的删除仅置 status、不设 deleted_at，以保留树结构）
- 点赞 / 收藏等**关系表使用物理删除**：行存在即关系成立，幂等依赖唯一索引，不引入软删
- 删除有子结构的节点（评论树）时保留占位（显示"该评论已删除"），不级联清空

### 8.3 列表接口分页

- 所有列表接口必须 **DB 级分页**（`LIMIT/OFFSET` 或 keyset），禁止先取全量 ID 再内存切页
- 分页参数经 `normPage` 规整（默认 10、上限 100）

### 8.4 错误码段位

新增业务错误码按模块段位分配，禁止跨段复用：

| 段位 | 模块 |
|------|------|
| 1xxxx | auth / user |
| 2xxxx | post |
| 3xxxx | comment |
| 4xxxx | circle |
| 5xxxx | file |
| 6xxxx | growth |
| 7xxxx | 预留（notification / search / follow） |

### 8.5 写操作幂等

- 高频写操作（发帖、评论）采用**同作者同内容时间窗去重**（Redis `SetNX`，10 秒窗口），窗口内重复提交返回 429
- 关系型写操作（点赞、收藏、关注、积分发放）依赖数据库唯一索引幂等

## 9. 去重与失效治理

- 发现过期文档时，直接删除或合并，不保留"可能有用"的重复副本
- 任一路由、核心参数、状态机变更时，同步更新关联文档
- 发版前执行一次文档巡检：按主题检查是否存在多份同类文档

## 10. 校验

```bash
bash scripts/check-docs.sh
```

校验 front-matter 完整性、字段格式、命名规范、历史版本节。建议接入 CI 或 pre-commit。
