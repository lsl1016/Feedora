# 未读数改为 Redis 缓存旁路

## 1. 背景与目标

`GET /notifications/unread-count` 是客户端高频轮询接口，原实现每次请求都执行数据库 `COUNT(user_id = ? AND read_status = 'unread')`。与此同时，Redis Key `notify:unread:{userID}` 由 Worker 在通知落库后 `Incr +1`，但没有任何读取方，也不在已读操作中扣减，形成只增不减的死数据。

本次改动将未读数改为 cache-aside 模式：读路径优先命中 Redis，未命中回源数据库并写回；写路径（通知落库、标记已读）统一删除缓存。目标：高频读取由 Redis 承接，同时消除只增不减的死数据。

## 2. 代码改动

- 文件：`internal/cache/cache.go`
  - 新增 `GetIntOK(ctx, key) (int64, bool)`：读取整型计数并区分「未命中」（Key 不存在、值不可解析或 Redis 未启用时返回 `(0, false)`）。既有 `GetInt` 无法区分「值为 0」与「Key 不存在」，cache-aside 的回源判断依赖该语义。
- 文件：`internal/service/notification_service.go`
  - `NotificationService` 注入 `cache.Cache`，`NewNotificationService` 签名增加 `cch` 参数。
  - 新增常量 `unreadCacheTTL = 10 * time.Minute`。
  - `UnreadCount` 改为 cache-aside：`GetIntOK` 命中直接返回；未命中执行仓储 `UnreadCount`（数据库 COUNT）并 `SetInt` 写回，TTL 10 分钟。
  - 新增 `invalidateUnread`；`MarkRead` / `MarkAllRead` 在仓储更新后调用（`cache.Del` 未读 Key）。
- 文件：`internal/worker/handlers.go`
  - `notify()` 通知落库成功后由 `Incr` 改为 `Del` 未读 Key：失效而非累加，下次查询回源数据库重建缓存。
- 文件：`internal/app/app.go`
  - 装配处改为 `service.NewNotificationService(notifRepo, cch)`。

## 3. 影响范围

- 接口：
  - `GET /notifications/unread-count`：读路径变化。Redis 命中时直接返回缓存值；未命中回源数据库 COUNT 并写回，高频场景由 Redis 承接。
  - `PUT /notifications/read-all`、`PUT /notifications/:notificationId/read`：对外行为不变，执行后增加缓存失效。
- 模块：notification（未读数读写路径）；cache 包新增 `GetIntOK` 方法。
- 配置：不新增配置项。`redis.enabled=false` 时 `GetIntOK` 恒未命中、`SetInt` / `Del` 为空操作，接口每次请求执行数据库 COUNT，行为与改动前一致。

## 4. 测试验证

- 命令：`go build ./...`、`go vet ./...`、`go test ./...`
- 结果：`go build ./...` 通过（exit 0）；`go vet ./...` 通过（exit 0）；`go test ./...` 结果 `ok github.com/feedora/backend/internal/api`，其余包无测试文件。集成路径未在真实 MySQL/Redis/Kafka 环境回归，以编译与现有单测验证。

## 5. 风险与兼容性

- 未读数存在最长 10 分钟的缓存窗口：缓存删除失败（Redis 异常）时以 TTL 过期兜底，期间接口可能返回滞后值。
- 存量脏数据：历史 `Incr` 写入的 `notify:unread:{userID}` 无 TTL，升级后首次读取会命中该历史累加值并原样返回；该 Key 在用户下一次收到通知或标记已读（触发 `Del`）前不会被清理，升级部署时可选择性清理存量 `notify:unread:*` Key。
- `MarkRead` / `MarkAllRead` 无论影响行数是否为 0 均执行一次 `Del`，对无未读通知的用户多一次空删除，无正确性影响。
- Redis 未启用的部署行为与改动前完全一致（每次数据库 COUNT）。
