# oss.type 配置生效

## 1. 背景与目标

配置键 `oss.type` 已在 `configs/config.yaml` 定义并被解析，但 `internal/app/app.go` 在装配存储时不读取该值，无条件构造 `LocalStorage`。配置为 `minio` / `aliyun` 的环境实际仍写本地磁盘且无任何提示，文件被写往非预期位置。

目标：让 `oss.type` 参与实现选择；对尚未实现的存储类型启动即报错（fail-fast），优于静默降级为本地磁盘。

## 2. 代码改动

- 文件：`internal/app/app.go`
  - 存储实例化改为 `switch cfg.OSS.Type`：
    - `case "", "local"`：构造 `ossx.NewLocalStorage(cfg.OSS.BasePath, cfg.OSS.PublicBaseUrl)`；
    - `default`（含 `minio`、`aliyun`）：返回错误 `不支持的 oss.type=%q（minio / aliyun 尚未实现，请使用 local）`，进程启动失败退出。

## 3. 影响范围

- 接口：`POST /files/upload` 行为不变（当前配置 `oss.type: local` 走 LocalStorage，上传路径、URL 拼装均无变化）。
- 模块：file（存储装配逻辑）；app 启动流程。
- 配置：`configs/config.yaml` 的 `oss.type` 生效。空字符串与 `local` 等价；配置为其他值时服务 fail-fast，启动输出上述错误信息。`oss.basePath`、`oss.publicBaseUrl` 仅在 local 分支被读取。

## 4. 测试验证

- 命令：`go build ./...`、`go vet ./...`、`go test ./...`
- 结果：`go build ./...` 通过（exit 0）；`go vet ./...` 通过（exit 0）；`go test ./...` 结果 `ok github.com/feedora/backend/internal/api`，其余包无测试文件。集成路径未在真实 MySQL/Redis/Kafka 环境回归，以编译与现有单测验证。

## 5. 风险与兼容性

- 此前将 `oss.type` 配成 `minio` / `aliyun` 的环境可以正常启动（实际使用本地磁盘），升级后启动直接失败；需将其改为 `local` 或留空，并确认存量文件的实际位置。
- 不涉及数据迁移：本地存储的文件与 `files` 表记录不受影响。
- 当前配置（`type: local`）的部署升级前后行为完全一致。
