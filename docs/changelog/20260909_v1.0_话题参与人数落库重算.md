# 话题参与人数落库重算

## 1. 背景与目标

`topics.participant_count` 在全部代码中没有写入逻辑，初始值恒为 0（种子数据亦不设置）。读取该字段的路径——话题广场 `tab=hot` 排序（`participant_count DESC, post_count DESC`）、话题榜单 DB 回退——实际退化为按 `post_count` 排序。

目标：为该字段建立落库重算路径，按「话题下未删除帖子的去重作者数」口径维护。

## 2. 代码改动

- 文件：`internal/repository/topic_repository.go`
  - 新增 `RecomputeParticipantCountsByPost(postID)`：单条 UPDATE 语句，按 `post_topics` 反查该帖子所属话题，将每个话题的 `participant_count` 置为子查询 `COUNT(DISTINCT p.author_id)`（JOIN `posts` 且 `deleted_at IS NULL`、`status <> 'deleted'`）。语句幂等，重复执行结果一致。
- 文件：`internal/worker/handlers.go`
  - 新增 `handleStat` 消费者（幂等名 `stat`，独立于 search / notification / growth / rank 的幂等记录）：`PostCreated` / `PostDeleted` 事件经 `idem.Claim(eventID, "stat")` 后按 `AggregateID`（帖子 ID）触发上述重算。
  - `handle()` 分发链末尾新增 `r.handleStat(ctx, m)`：全部事件进入该消费者，仅上述两类事件有实际动作。

## 3. 影响范围

- 接口：无接口变更。话题广场 `tab=hot` 与话题榜单 DB 回退的排序数据源随 `participant_count` 重算生效。
- 模块：topic（`participant_count` 产生写入路径）；worker 新增第 5 个消费者 `stat`。
- 配置：不新增配置项。链路依赖 worker + Kafka 启用：`kafka.enabled=false` 时不产生任何重算，字段仍为 0，可用 `scripts/recount.sql` 第 4 节一次性校准（该脚本口径为 `status = 'published'`，比事件重算口径「排除 deleted、含 hidden」更严格）。

## 4. 测试验证

- 命令：`go build ./...`、`go vet ./...`、`go test ./...`
- 结果：`go build ./...` 通过（exit 0）；`go vet ./...` 通过（exit 0）；`go test ./...` 结果 `ok github.com/feedora/backend/internal/api`，其余包无测试文件。集成路径未在真实 MySQL/Redis/Kafka 环境回归，以编译与现有单测验证。

## 5. 风险与兼容性

- 重算仅由 `PostCreated` / `PostDeleted` 触发，且只覆盖该帖子关联的话题：帖子隐藏 / 恢复不触发重算，重算口径含 hidden 帖，`participant_count` 与「话题下可见帖子作者数」存在口径差异。
- 依赖 Kafka：未启用 Kafka 的部署该字段保持 0，`hot` 分类继续按 `post_count` 排序，行为与改动前一致。
- 每次帖子创建 / 删除对关联话题执行一次多行 UPDATE，绑定话题数多的帖子写放大更明显；幂等名 `stat` 独立，事件重投不重复执行。
- `post_topics` 存在孤儿关联（`topic_id` 指向不存在话题）时，UPDATE 的 WHERE 子查询限定在关联话题内，孤儿记录不引发错误。
